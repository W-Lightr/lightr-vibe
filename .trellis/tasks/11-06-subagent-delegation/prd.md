# 通用子代理委派与会话展示

## Goal

让用户能在一个父 Agent 会话中委派多个相互独立的子任务，并在同一应用里看到子代理状态、处理其交互请求、取消任务和查看完整子会话。能力必须跨已接入的 ACP 引擎通用，而非依赖 Codex 的专有协作协议。

## Confirmed Facts

- 当前应用以 Tauri + Vue 实现；每个本地 `Session` 独占一条 ACP 连接与 Agent 进程。`src-tauri/src/acp.rs` 的 `CONNS` 已按本地会话 id 管理连接，前端以该 id 路由 `acp://update`、权限和提问事件。
- 已有会话、消息、工具调用和索引持久化模型：`src/types/session.ts`、`src/stores/session.ts`。当前 `Session` 没有父子关系，普通 `ToolCall` 也没有委派任务语义。
- 当前 ACP `session/new` / `session/load` 已通过 `mcpServers` 注入本地 `ask_user_question` 伴生 MCP；可将这是通用委派 MCP 的接入点。
- ACP 本身定义独立 Agent 会话的连接和流式更新，但不定义跨 Agent 的“创建子代理 / 任务状态 / 取消”控制面。
- 参考项目 codeg 的通用路径是 MCP `delegate_to_agent` / `get_delegation_status` / `cancel_delegation` → 宿主 delegation broker → 独立子 ACP 会话；codeg 的 Codex `collabAgentToolCall` 仅是专有展示增强。
- 已接入的引擎为 OpenCode、Claude Code 和 Codex；均应能作为子代理的引擎候选，但仅限用户设备上已可用的引擎。

## In Scope

1. 提供跨引擎的本地 MCP 委派工具：创建委派、查询状态、取消委派；父 Agent 可并行委派多个一级子任务。
2. Rust 侧 delegation broker：校验请求、创建和持久化子会话、启动独立 ACP 子会话、发送首条任务、汇总终态和取消级联。
3. 父子会话关系与委派任务持久化；重启后可恢复历史关联和已完成状态。
4. 父会话内的专用委派卡片：显示 Agent、任务摘要、状态、错误和“查看会话”入口；连续状态轮询不应刷屏。
5. 委派子会话创建后，自动展开右侧栏并切换到该子会话；右侧抽屉展示完整消息流，子代理的权限请求和用户提问按子会话路由并能在该界面完成。委派卡片保留“查看会话”入口，供用户关闭后重新打开。
6. Codex 原生协作工具调用的兼容渲染：识别到稳定子线程信息时复用委派卡片；没有可访问线程时只展示摘要，不伪造会话入口。
7. 设置入口：委派功能总开关、最大委派深度的安全限制，以及运行条件/风险的用户可见说明。

## Out of Scope

- 跨机器、云端或远程主机的子代理。
- 自动下载、安装或更新 Agent/ACP 适配器。
- 自动合并子代理产出的代码、自动 Git 提交，或任务看板状态自动迁移。
- 二级及以上递归委派作为首版默认能力；首版默认只支持一级，是否放开由深度设置控制。
- 将 Codex 专有协作协议作为唯一或必要的委派方式。

## Requirements

### R1 — 通用委派控制面

父 Agent 可以通过宿主提供的 MCP 工具提交自包含任务，指定可用引擎和可选工作目录；工具立即返回稳定任务 id，子代理异步运行。查询操作返回运行、完成、失败、已取消及等待用户交互等状态；取消操作只影响指定任务及其子会话。

### R2 — 子会话隔离与生命周期

每次委派创建独立本地 Session、ACP 连接和 Agent 进程。子会话继承经校验的工作目录，不继承父会话的完整消息历史；父 Agent 必须在任务文本中提供必要上下文。父会话关闭或取消时，仍在运行的直属子任务必须被取消。

### R3 — 安全边界

仅允许在父会话所属项目根目录（或其子目录）中运行；临时会话沿用其受控临时目录。需拒绝非法引擎、越界路径、超出深度和失效父会话。子代理的工具权限与提问必须独立于父会话处理，不得被静默自动批准。

### R4 — 会话与任务可恢复

父子关系、任务标识、最终状态和可显示的结果摘要须落入本应用的 `~/.lightr-vibe/lightr-vibe/` 命名空间；不能读写同级其他应用数据。应用重启后，历史委派卡片仍可定位子会话；未完成的旧任务必须以明确中断/失败态恢复，不能误报运行。

### R5 — 可理解的展示

父会话将 `delegate_to_agent`、状态查询、取消操作渲染成委派专用组件，而不是裸 MCP 工具名称。卡片包含任务摘要、子代理引擎、短任务 id、状态/错误和可用时的会话入口；状态以事件驱动刷新，轮询记录应合并。

### R6 — Codex 兼容增强

Codex 专有协作工具调用可映射至相同视觉语言，但通用委派流程不依赖该数据。缺少稳定子会话引用时，界面只能展示已知状态和文本，不能提供不可用的“查看会话”。

## Acceptance Criteria

- [ ] 用户启用委派后，父会话可将两个独立任务并行委派给任意两个可用引擎；父 Agent 可通过稳定任务 id 查询和取消每一个任务。
- [ ] 每个委派都有独立子 Session、ACP 连接和工作目录；子 Agent 不会获得父会话未在任务中提供的聊天历史。
- [ ] 父会话中显示专用委派卡片，运行、完成、失败、取消和等待权限/提问五种状态都可区分；连续查询不会生成冗余卡片。
- [ ] 收到新子代理的 `delegation://started` 事件后，应用自动展开右侧栏并展示该子会话；若用户关闭抽屉，父会话委派卡片仍可重新打开它。
- [ ] 点击可用的“查看会话”会在右侧打开子会话，实时内容、权限卡和提问卡按子连接 id 正确路由。
- [ ] 关闭/取消父会话会取消直属运行中子任务；取消一个子任务不会取消其同级任务或父会话。
- [ ] 非法工作目录、不可用引擎、超出深度、子 Agent 无输出/鉴权失败/异常退出都产生可理解的失败状态，不崩溃也不无限等待。
- [ ] 重启后历史委派卡片及其子会话仍可打开；重启时未完成任务明确显示为中断/失败。
- [ ] OpenCode、Claude Code、Codex 均能走同一 MCP → broker → ACP 子会话链路；Codex 原生协作展示不影响通用链路。
- [ ] 既有单 Agent 会话、权限、提问和浏览器 mock 流程无回归。

## Key Decisions

- **授权策略（用户确认，2026-11-06）**：委派总开关默认关闭。用户在设置中主动启用后，父 Agent 可直接调用委派 MCP 创建子代理，无需逐次确认；子代理自身的权限和提问仍必须由用户逐项处理。
- **协议边界（用户确认）**：通用路径固定为 MCP 委派控制面 + 独立 ACP 子会话；Codex 专有协作只做兼容展示，不能成为前置依赖。
